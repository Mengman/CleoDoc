# CleoDoc 文档处理设计

> 状态：设计讨论稿，尚未实现行号读取与局部写入  
> 日期：2026-08-04  
> 适用范围：v0.1 CLI Core、后续 RAG 上下文和 v0.2 作品工作室  
> 相关文档：[产品需求](./PRD.md) · [技术架构](./TECHNICAL_ARCHITECTURE.md) · [开发计划](./DEVELOPMENT_PLAN.md) · [Tool Call 设计](./TOOL_CALL_DESIGN.md)

## 1. 文档目的

文档处理是 CleoDoc 的核心基础设施，不只是“读取和覆盖一个 Markdown 文件”。随着产品发展，LLM 读取的文档内容还需要携带行号、资料引用、用户批注、重点标记、格式、知识状态和其他结构信息，并支持安全、精确、可审批的局部修改。

本文统一记录：

- CleoDoc 如何向 LLM 表达文档内容。
- LLM 如何按行读取、替换、删除和插入内容。
- 行号、换行和文档变化的基础语义。
- Tool Result、审批、压缩投影和安全边界。
- 后续批注、引用、格式和结构化编辑的研究方向。

当前已经实现的 `read_project_document` 使用字符偏移读取，`write_project_document` 只支持创建或全文替换。本文所述行号读取和局部写入仍是待开发设计，不得在实现状态文档中标记为已完成。

## 2. 已确认的产品需求

### 2.1 所有文档读取都携带行号

行号不是一个额外的专用读取功能，而是 CleoDoc 向 LLM 提供文档内容时的基础结构信息。现阶段先只返回行号和文本，未来再扩展资料引用、批注、重点标记和格式。

不再同时提供“普通读取”和“带行号读取”两套重叠 Tool。现有 `read_project_document` 应升级为带行号的读取协议。

### 2.2 文档写入支持四类操作

1. 创建文档或全文替换。
2. 按闭区间行号替换内容，例如替换第 10–40 行。
3. 按闭区间行号删除内容。
4. 在某一行之后插入内容。

删除应使用明确的删除操作，不把空字符串隐式解释为删除。这样可以避免漏填内容导致误删除，并让审批、日志和错误恢复保持清晰。

### 2.3 行号是读取快照的坐标

行号只描述某一次读取时的文档位置，不是正文的一部分，也不是跨版本永久稳定的段落 ID。文档修改后，后续行号可能整体移动；LLM 在继续执行局部编辑前需要重新读取受影响范围。

## 3. 设计原则

- **单一读取协议**：LLM 读取项目文档时始终获得行号，不需要选择另一种 Tool。
- **结构与正文分离**：行号和未来元数据不能混入 Markdown 正文，也不能在写入时被复制回文件。
- **明确操作语义**：全文替换、行替换、行删除和行后插入使用清楚的操作边界。
- **防止陈旧写入**：局部写入必须基于最近一次读取的文档状态，不能使用已经失效的行号静默修改新内容。
- **审批优先**：所有 LLM 发起的写入继续要求用户批准，批准前展示目标和变化。
- **原子写入**：校验失败、审批拒绝或写入异常不能留下部分修改。
- **低 Token 投影**：Tool Result 和压缩投影只返回后续决策必需的结构信息，不重复正文。
- **面向未来扩展**：当前结构允许以后加入引用、批注和格式，但不提前实现没有进入范围的复杂模型。

## 4. LLM 可见文档投影

### 4.1 当前最小结构

建议建立统一的 LLM 可见文档片段：

```ts
interface DocumentSegment {
  path: string;
  updatedAt: string;
  startLine: number;
  endLine: number;
  totalLines: number;
  lines: DocumentLine[];
  truncated: boolean;
  nextLine: number | null;
}

interface DocumentLine {
  lineNumber: number;
  text: string;
}
```

`DocumentLine` 中的 `lineNumber` 是 CleoDoc 生成的坐标，`text` 才是原始正文。Tool 描述和 System Prompt 必须明确禁止把 `lineNumber` 写入文档。

### 4.2 不使用行号文本前缀

不采用以下形式：

```text
10: 雨水沿着旧车站的玻璃缓缓滑落。
11: 林默站在没有灯光的候车室里。
```

这种格式容易让模型误以为 `10:` 是正文。应使用结构化的 `lineNumber + text`，使文档坐标和原文保持明确分离。

### 4.3 未来元数据

以后可以在文档投影中增加可选元数据，例如：

```ts
interface FutureDocumentLine extends DocumentLine {
  references?: ReferenceMark[];
  annotations?: UserAnnotation[];
  highlights?: HighlightRange[];
  comments?: CommentReference[];
  formatting?: TextFormattingRange[];
}
```

未来可能表达：

- 某一行或字符范围引用了哪份资料。
- 用户添加的批注、重点符号或审阅意见。
- 某段文字对应的知识候选、冲突或批准事实。
- 当前内容来自正式正文、工作 Draft 或待审批变更。
- Markdown、富文本或编辑器中的结构与格式。

这些信息由 CleoDoc 在读取时从正文事实源、SQLite 投影和后续编辑器元数据中合并，不直接污染 Markdown 正文。具体范围模型、坐标更新和存储方式尚未设计。

## 5. `read_project_document` v2

### 5.1 定位

现有 `read_project_document` 应升级为按行读取，不新增 `read_project_document_lines`。这是不兼容的 Input/Output 变化，Tool 版本需要从 v1 提升到 v2。

### 5.2 Input

```ts
interface ReadProjectDocumentInputV2 {
  document: string;
  startLine?: number;
  maxLines?: number;
}
```

- `document`：`manuscript` 下的项目相对路径。
- `startLine`：从 1 开始，默认 1。
- `maxLines`：本次最多读取的行数；建议初始默认值为 200，最终上限通过上下文预算和测试确定。

### 5.3 Output

```ts
interface ReadProjectDocumentOutputV2 {
  document: DocumentSegment;
}
```

示例：

```json
{
  "document": {
    "path": "manuscript/chapter-01.md",
    "updatedAt": "2026-08-04T10:20:30Z",
    "startLine": 10,
    "endLine": 12,
    "totalLines": 186,
    "lines": [
      {
        "lineNumber": 10,
        "text": "雨水沿着旧车站的玻璃缓缓滑落。"
      },
      {
        "lineNumber": 11,
        "text": "林默站在没有灯光的候车室里。"
      },
      {
        "lineNumber": 12,
        "text": ""
      }
    ],
    "truncated": true,
    "nextLine": 13
  }
}
```

读取结果不返回 `contentHash`、数据库文档 ID、FTS Rank 或其他内部字段。

## 6. 文档写入 Tool

### 6.1 `write_project_document`

继续负责：

- 创建新的 Markdown 文档。
- 全文替换已有文档。

已有文档只有在模型明确声明全文替换意图并获得用户批准后才能覆盖。是否要求全文替换也携带 `expectedUpdatedAt`，仍需在实现前确认。

### 6.2 `replace_project_document_lines`

替换指定闭区间内的完整行：

```ts
interface ReplaceProjectDocumentLinesInput {
  path: string;
  startLine: number;
  endLine: number;
  content: string;
  expectedUpdatedAt: string;
}
```

规则：

- `startLine` 和 `endLine` 均包含在替换范围内。
- `startLine` 必须小于或等于 `endLine`。
- `content` 可以包含一行或多行，替换后的行数不需要等于原行数。
- `content` 不允许为空；删除使用独立 Tool。
- 执行前校验文档状态和行号范围。

### 6.3 `delete_project_document_lines`

删除指定闭区间内的完整行：

```ts
interface DeleteProjectDocumentLinesInput {
  path: string;
  startLine: number;
  endLine: number;
  expectedUpdatedAt: string;
}
```

删除全部行会产生空文档，不等于删除文件。删除整个文件仍属于独立的文档管理操作。

### 6.4 `insert_project_document_after_line`

在指定行之后插入内容：

```ts
interface InsertProjectDocumentAfterLineInput {
  path: string;
  afterLine: number;
  content: string;
  expectedUpdatedAt: string;
}
```

规则：

- `afterLine = 0` 表示插入到文档最前面。
- `afterLine` 等于最后一行表示追加到文档末尾。
- 空文档只允许使用 `afterLine = 0`。
- `content` 不允许为空。
- Tool 负责处理插入内容与前后原文之间的换行边界。

## 7. 行号与换行语义

当前设计采用以下基础语义：

- 行号统一从 1 开始。
- 替换和删除范围使用闭区间。
- `\r\n` 和 `\n` 都只表示一次换行。
- 文件末尾的换行符不额外产生一条可编辑空行。
- 空文档没有第 1 行；在空文档开头插入使用 `afterLine = 0`。
- 行号和结构元数据不属于正文，不能写回文件。
- 局部操作完成后，后续行号可能变化；继续编辑前应重新读取。

以下问题仍待实现前通过固定样例确认：

- 保存时保留原文件换行风格，还是统一为 UTF-8 + LF。
- 替换内容末尾换行的规范化规则。
- 超长单行对读取上限和上下文预算的影响。

## 8. 防止陈旧写入

局部写入建议要求 `expectedUpdatedAt`，其值来自最近一次 `read_project_document`。执行前比较当前文档状态：

- 一致：可以进入审批和写入。
- 不一致：返回稳定错误 `DOCUMENT_CHANGED`，要求重新读取。
- 用户或其他 Tool 修改过文档后，旧行号不能继续使用。

`updatedAt` 是当前已经允许向 LLM 暴露的业务字段，不需要暴露内部 Hash 或 Revision。文件系统时间精度是否足以作为可靠并发条件需要通过跨平台测试确认；如果不足，应设计独立的模型可见文档版本令牌，而不是退回暴露数据库内部字段。

## 9. 公共写入结果

局部和全文写入可以共享紧凑的模型可见结果：

```ts
interface ProjectDocumentMutationResult {
  document: {
    path: string;
    operation:
      | "created"
      | "replaced"
      | "lines_replaced"
      | "lines_deleted"
      | "lines_inserted";
    updatedAt: string;
    originalStartLine?: number;
    originalEndLine?: number;
    resultingStartLine?: number;
    resultingEndLine?: number;
    removedLineCount: number;
    insertedLineCount: number;
    totalLines: number;
  };
}
```

结果不返回正文、`contentHash`、数据库 Row ID 或内部 Revision。它需要让模型知道实际操作、行数变化和是否应该重新读取。

## 10. 审批与写入流程

所有 LLM 发起的写操作保持 `approval: "ask"`：

```text
读取带行号的文档片段
→ LLM 选择全文替换、行替换、删除或插入
→ CleoDoc 校验路径、文档状态和行号
→ 展示目标范围和修改预览
→ 用户批准
→ 再次校验文档状态
→ 原子写入
→ 返回更新时间和行数变化
```

审批界面至少应展示：

- 文档相对路径。
- 操作类型。
- 原始行号范围。
- 被替换或删除的原文。
- 准备写入的新内容。
- 修改前后的行数变化。

当前 Tool Interface 只把 Input 交给审批处理器，如何在执行前生成包含旧内容的 Diff 预览仍需单独设计。不能为了快速实现而在审批后才第一次展示被删除或替换的原文。

## 11. 文件安全与一致性

- 所有路径必须限制在当前项目 `manuscript` 范围内。
- Tool 参数必须通过 Zod Schema 校验。
- 写入使用临时文件、同步和原子替换，不直接修改原文件的一部分。
- 校验失败、用户拒绝、文档变化或磁盘错误不得留下部分写入。
- 写入成功后再返回新的 `updatedAt` 和行数。
- 局部编辑引擎应实现为不依赖 CLI、Electron 或 Provider 的纯 Core 能力。
- 普通聊天、Tool Result 和 Debug 日志不能意外保存第二份正文事实源。

## 12. Session 压缩投影

文档读取和写入的历史 Tool 参数可能包含大段正文，不能原样进入 Session 压缩。建议投影：

| Tool | 允许进入压缩的信息 |
|---|---|
| `read_project_document` | 路径、更新时间、读取起止行、总行数、是否截断 |
| `write_project_document` | 创建/全文替换、路径、更新时间、写入后总行数 |
| `replace_project_document_lines` | 路径、更新时间、原范围、结果范围、删除/插入行数 |
| `delete_project_document_lines` | 路径、更新时间、删除范围、删除行数、剩余总行数 |
| `insert_project_document_after_line` | 路径、更新时间、插入位置、插入行数、写入后总行数 |

压缩投影不得包含：

- 读取到的正文。
- 写入参数中的正文。
- 用户批注或资料原文。
- `contentHash`、数据库 ID 或内部 Revision。

## 13. 与 RAG 和未来 GUI 的关系

`DocumentSegment` 不应只服务于文件 Tool。后续可以作为统一的 LLM 可见文档投影，用于：

- `read_project_document` 的直接读取。
- RAG 命中的正文证据。
- 场景创作时的上下文装箱。
- 用户批注、资料引用和重点标记。
- Draft 页面与正文编辑器。
- 一致性检查和影响分析结果。

RAG 内部 Chunk 仍有自己的稳定 ID、内容哈希和结构路径；向 LLM 展示时再映射为可理解的文档路径、行号范围、正文和允许披露的元数据。不要让 SQLite 行、FTS Rank 或索引实现成为文档协议。

## 14. 后续研究方向

### 14.1 多个不连续范围的原子修改

模型可能需要同时修改同一文档的多个位置。逐次修改会导致后续行号移动。首版保持一次调用只修改一个连续范围；模型需要重新读取，或者从文档后方向前修改。

未来可以研究批量操作，在同一文档状态上校验全部范围，并通过一次审批和一次原子写入完成。首版不提前实现复杂批量 Schema。

### 14.2 标题、场景和稳定块定位

行号适合当前 Markdown 和 CLI，但不是长期稳定标识。未来可以研究：

- 按 Markdown 标题读取和替换。
- 按场景、段落或稳定块 ID 定位。
- TipTap/ProseMirror 节点与 Markdown 行号之间的映射。
- 外部编辑后稳定块身份的恢复。

### 14.3 字符范围标注

批注、重点标记和资料引用可能只覆盖一行中的部分文字，需要定义 Unicode 安全的范围坐标、重叠规则以及正文变化后的锚点恢复。当前阶段不固定字段和数据库结构。

### 14.4 格式协议

未来 CleoDoc 可能使用 `cleodoc-richtext-v1` 或其他自定义格式。需要研究：

- Markdown 与富文本的双向转换。
- LLM 可见结构的 Token 成本。
- 格式标记与正文统计的边界。
- 格式、批注和知识元数据是否分层传输。
- 不同 Provider 对大型结构化 Tool Result 的可靠性。

## 15. 当前不做

- 不在首版实现任意 JSON Patch、unified diff 或模糊文本补丁。
- 不让 LLM 直接操作绝对路径、文件字节偏移或数据库记录。
- 不把空替换内容隐式解释为删除。
- 不在首版实现多个不连续范围的批量事务编辑。
- 不提前固定批注、重点标记和富文本的数据库 Schema。
- 不用行号替代未来的稳定块、版本和 ChangeSet。

## 16. 待确认问题

1. 全文替换是否也强制要求最近一次读取返回的 `expectedUpdatedAt`。
2. `updatedAt` 在 Windows、macOS 和 Linux 上是否足以承担并发保护；是否需要模型可见的文档版本令牌。
3. `maxLines` 的默认值和硬上限。
4. 保存时保留原换行风格还是统一为 LF。
5. 审批前 Diff 由 Tool、Runtime 还是独立文档编辑服务生成。
6. 局部写入 Tool 是否首版全部设为 `full`，还是通过 `project_tool_catalog` 按需披露。
7. `write_draft` 的文档引用和版本语义如何与通用文档处理协议统一。

## 17. 建议实施顺序

1. 建立确定性的行拆分、行计数和换行测试样例。
2. 将 `read_project_document` 升级到 v2，返回 `DocumentSegment`。
3. 实现不依赖 Tool Runtime 的纯文档局部编辑服务。
4. 增加行替换、删除和行后插入 Tool 及 Schema。
5. 补充文档状态预检、审批预览和写入前二次校验。
6. 更新 Tool 压缩投影、System Prompt 和 CLI 审批展示。
7. 使用 Fake Provider 覆盖读取、修改、冲突、拒绝和重试闭环。
8. 再研究批量编辑、稳定块、批注、引用和富文本投影。

## 18. Draft 写入与文本统计

### 18.1 背景

LLM 很难仅凭自身生成过程准确估计中文文稿的实际字数。在长篇创作测试中，模型给出的估算可能与实际结果相差一千字以上。CleoDoc 需要提供确定性的本地统计，让主笔知道“刚刚实际写了多少”，再由主笔判断是否继续写作、补充内容、修订或向用户询问。

这项能力不是字数约束器：

- 系统不根据目标字数截断、拒绝或自动重写模型输出。
- 普通对话不统计字数，也不向上下文持续注入无意义的计数信息。
- 统计结果只反馈已经成功写入 Draft 的内容，不能以流式片段或模型自报数字代替。

最初考虑过让模型先在聊天中输出文稿，再由系统识别并写入 Draft。该方式会让同一正文同时出现在聊天窗口和 Draft 页面，形成重复展示、重复存储语义和不清晰的事实来源。也考虑过自定义 `agent` 消息角色用于主动状态报告，但 Provider 协议并不普遍支持该角色，标准 `tool` 结果已经能够承担机器反馈。

最终采用直接 Tool Call：当主笔决定产出文稿时，不在 Assistant Content 中输出正文，而是直接调用 `write_draft`。正文只进入 Draft，Tool 返回精确统计，模型据此决定下一步。

### 18.2 目标

- 正文只在 Draft 工作区展示一次，不复制到聊天消息中。
- 对每次成功写入提供确定性的字符数、字数和标点符号数。
- 用紧凑 Tool Result 将统计反馈给模型，尽量少占用上下文。
- 允许模型在得到统计后自然地继续写、停止或向用户说明判断。
- 保持 Draft 写入可恢复、可审计、可重试，并保护已批准正文。
- 统计器和 Draft Application Service 可由 CLI 测试，并由未来 GUI 复用。

### 18.3 非目标

- 不要求模型在写作前严格满足指定字数。
- 不为普通聊天内容计算或展示文稿统计。
- 不通过 `finish_draft` 声明“写完”；模型停止调用 `write_draft` 即表示本轮不再写入。
- 不在当前阶段确定最终自定义排版格式、章节总字数展示或数据库表结构。
- 不允许 `write_draft` 直接覆盖用户已经批准的正式正文。

## 19. Draft 核心交互协议

### 19.1 单轮输出模式

每个 Assistant 轮次必须在以下模式中选择一种：

1. **沟通模式**：输出普通 Assistant Content，用于解释、评审、提问和交付说明；不调用 `write_draft`。
2. **文稿模式**：Assistant Content 为空，直接调用 `write_draft`，正文放在 Tool 参数的 `content` 中。

同一轮不得同时输出面向用户的正文和调用 `write_draft`。这能保证正文只出现在 Draft 页面，聊天区域只显示紧凑的写入状态卡片。

### 19.2 Tool Loop 结束条件

`write_draft` 成功后，标准 `tool` 角色把写入结果和统计返回给模型，Tool Loop 再给模型一个决策轮次：

- 需要继续写：再次调用 `write_draft`。
- 需要查询资料或正文：调用相应读取或 RAG Tool。
- 已完成当前工作：不再调用 Tool，输出简洁的交付说明。
- 需要用户判断：不再调用 Tool，说明实际结果和建议并提问。

不设计 `finish_draft`。如果模型认为文稿已经完成，只需停止发起 `write_draft`。Draft 始终是当前可编辑的工作状态，不需要额外的“完成/重新打开”状态机。

Agent 回合遵循统一结束规则：

- 存在 Tool Call：继续 Tool Loop。
- 没有 Tool Call且存在有效 Assistant Content：结束本轮并交还用户。
- Tool Call 和有效 Assistant Content 都不存在：视为无效模型输出。
- 达到最大轮数、总时限、费用上限或收到取消信号：中止本轮，不继续自动写入。

### 19.3 用户可见反馈

聊天窗口不展示 `write_draft.content`，只展示例如“已向第一章追加 1,684 字”的状态卡片。该卡片是本地 UI 投影，不创建自定义 LLM 消息角色。

模型不应把 Tool Result 当成用户发言，不要以“好的，你刚刚告诉我……”等对话格式复述机器状态。需要用户决策时，应直接给出创作判断，例如：

> 当前章节已经写到约 3,200 字，但人物冲突还没有充分展开。我建议继续补充两人的正面交锋，你希望我继续吗？

如果不需要用户决策，模型可以直接继续调用 `write_draft`，无需发送过渡性致谢或确认。

## 20. `write_draft` Tool

### 20.1 与通用文档 Tool 的边界

当前 CLI `write_project_document` 是通用的、逐次用户审批的项目文件写入 Tool；未来 `write_draft` 是主笔创作循环中的专用工作草稿 Tool。二者不能复用相互矛盾的审批、展示和完成语义。

`write_draft` 只修改可恢复的工作 Draft，不直接覆盖已批准正文或作品 Canon。Draft 进入正式正文仍通过后续交付、ChangeSet 和用户审批完成。

### 20.2 输入契约讨论稿

原 Draft 设计提出以下目标契约：

```ts
interface WriteDraftInput {
  documentId: string;
  operation: "append" | "replace" | "patch";
  baseRevision: number;
  format: "markdown-v1" | "cleodoc-richtext-v1";
  content: string;
}
```

- `documentId` 表示当前 Project 内经过授权的文档引用，不接受任意文件路径。
- `operation` 的首个实现可以只支持 `append`，后续再增加 `replace` 和 `patch`。
- `baseRevision` 用于乐观并发检查，防止覆盖用户或其他任务的新修改。
- `format` 明确选择对应的格式解析器和文本提取器，不能靠内容猜测格式版本。
- `content` 是本次待写入的完整文稿；正文不再同时出现在 Assistant Content 中。

该契约中的 `documentId` 和 `baseRevision` 需要与本文的通用文档引用、`updatedAt` 前置条件及“不暴露数据库内部字段”原则重新统一，目前不能直接视为最终公共 Schema。实施前必须完成第 16 节第 7 项待确认问题。

Tool 参数可能由 Provider 以多个流式增量返回。模型适配器必须先完整拼接同一个 Tool Call 的参数 JSON，再进行 Schema 校验和写入；未完成或无法解析的参数不得产生部分文档。

### 20.3 输出契约讨论稿

首个版本至少返回本次写入的三项统计：

```ts
interface WriteDraftResult {
  status: "written";
  documentId: string;
  revision: number;
  written: TextStatistics;
}
```

示例：

```json
{
  "status": "written",
  "documentId": "chapter-01",
  "revision": 4,
  "written": {
    "characters": 2017,
    "words": 1684,
    "punctuation": 225,
    "algorithmVersion": "cleodoc-text-statistics-v1"
  }
}
```

`documentId` 和 `revision` 同样属于待统一字段。无论最终如何命名，Tool Result 都必须紧凑，不重复正文、Prompt 或长篇解释。结果使用标准 `tool` 角色进入当前 Tool Loop；聊天 UI 可以将其渲染为状态卡片，但不得伪装成用户消息。

后续只有在确有产品需要时才增加写入后整篇文档的总统计。首个版本不把章节总字数作为必需条件。

### 20.4 写入语义

- 一次成功调用同时产生新 Draft 版本和该次写入统计；不能出现“文档已写入但结果仍报告失败”的不确定状态。
- 文件或 Draft 事实源使用安全写入；相关运行状态在事实源成功后再更新。
- 同一个 Tool Call 必须具有稳定的幂等键。网络重试、Provider 重放或进程恢复不能造成重复追加。
- 文档版本不匹配、格式不支持、内容为空、Schema 无效或项目作用域不符时，不进行部分写入，返回结构化 Tool 错误。
- Draft 到正式正文仍通过后续交付、ChangeSet 和用户审批完成。

## 21. 文本统计规范

### 21.1 公共类型

```ts
interface TextStatistics {
  characters: number;
  words: number;
  punctuation: number;
  algorithmVersion: "cleodoc-text-statistics-v1";
}
```

`algorithmVersion` 必须随结果保存或返回。未来规则变化时可以重新计算和解释历史差异，不能在同一版本下静默改变算法。

### 21.2 字符数

字符数是 `write_draft.content` 原始字符串中的字符数量：

- 包含正文、格式标记、标点、空白和换行。
- 不对原始内容做 Unicode 规范化后再计数。
- 使用 Unicode Code Point 数量，而不是 JavaScript UTF-16 Code Unit 数量；建议实现为 `Array.from(content).length`。

该定义统计模型实际提交给 Tool 的内容。换行风格如果在保存阶段发生平台转换，不应反向改变“本次写入字符数”。

### 21.3 可见文本提取

字数和标点符号数都先排除格式相关字符，再对可见文本统计。实现必须按 `format` 使用解析器或 AST 提取器，不能用一组正则表达式猜测格式。

以 Markdown 为例：

- 标题符号、强调符号、代码围栏和链接语法不计入字数或标点。
- 标题文字、强调文字和链接显示文字属于可见文本，应保留。
- 链接目标、属性和结构性标记不属于可见文稿，应排除。

未来 `cleodoc-richtext-v1` 必须提供独立的纯文本提取器，但沿用相同的统计接口。

### 21.4 字数

字数在可见文本上计算：

- 每个汉字字符计为一个字。
- 每个连续的英文单词计为一个字。
- 格式字符、空白和标点符号不计入字数。
- 英文缩写中的内部撇号允许保持为一个英文单词，例如 `don't` 和 `writer's` 各计一个字；撇号本身仍按标点规范计数。

数字、其他语言文字和特殊符号如何纳入“字数”仍是开放规则，首个实现前必须用固定测试样例确认。

### 21.5 标点符号数

标点符号数在可见文本上计算：

- 排除所有格式相关字符。
- 使用 Unicode Punctuation 类别 `\p{P}` 逐字符统计中英文标点。
- 空白、Emoji 和一般数学/货币符号不自动视为标点。

### 21.6 示例

原始 Markdown：

```md
**你好，world!**
```

统计结果：

- 字符数：13，包括四个 `*` 格式字符。
- 字数：3，即“你”“好”和 `world`。
- 标点符号数：2，即“，”和 `!`。

### 21.7 本次写入与整篇文档

`written` 必须对本次 `write_draft.content` 精确计算。未来如增加整篇文档总统计，应在写入成功后的最终文档上重新计算，不能简单把历史分段相加；两次写入的英文、数字或格式边界可能在拼接处形成不同的词法单元。

## 22. Draft 上下文、持久化与 Prompt

### 22.1 上下文与消息持久化

`write_draft.content` 在当前 Tool Call 参数中已经出现一次，Tool Result 只返回文档引用、版本或更新时间、统计和必要状态，不能再次携带正文。这样模型可以立即依据统计决策，同时避免在下一轮上下文中重复同一内容。

用于聊天展示和检索时应遵守：

- 不把 Draft 正文复制为普通 Assistant Message Content。
- 不把 Tool 参数中的正文索引为普通对话正文，否则历史搜索会得到重复内容。
- UI 状态卡片只引用 Tool Call、文档和版本状态，不保存第二份正文。
- 活跃上下文增长后，较早的 `write_draft` 只投影为文档引用、版本状态和写入范围，不包含正文或内部 Hash；模型需要原文时通过受控文档读取 Tool 获取。
- 压缩、历史查询和 Debug 日志必须明确区分 Tool 元数据与文稿正文。

具体数据库字段和 Draft 版本表结构在实现前随文档版本模型一并设计，本文不提前固定 Schema。

### 22.2 Prompt 约束

主笔 System Prompt 应包含等价规则：

> 与用户沟通时输出普通 Assistant Content。需要创作文稿时，不要把文稿放在 Assistant Content 中，直接调用 `write_draft`，并把文稿放入 `content` 参数；同一轮不能混合两种模式。收到写入统计后，自行判断继续写入、结束交付或向用户询问，不要感谢、复述 Tool Result，也不要把 Tool Result 当成用户发言。

Prompt 只规定行为边界，不要求模型预先精确预测字数。精确数字始终由本地统计器产生。

## 23. Draft 异常与协议违规

- 模型同时输出长篇正文和 `write_draft`：视为协议违规，不自动写入 Assistant Content；允许一次有针对性的纠正重试，仍失败则向用户报告。
- 预期产出文稿但模型只输出长篇普通 Content：不通过启发式规则静默转存，避免误把解释或引用写入 Draft。
- Tool 参数流中断或 JSON 无效：丢弃未提交内容，保留原 Draft 版本。
- 写入超时但本地结果未知：用幂等键查询既有执行结果，不能盲目重试追加。
- 文档版本冲突：返回可理解的冲突状态，由模型重新读取或交给用户处理。
- 统计失败：本次写入事务不应返回成功；在无法提供可信统计前，不让模型基于错误数字继续决策。

## 24. Draft 测试与验收

### 24.1 统计单元测试

- 纯中文、纯英文和中英混排。
- 中文全角标点、英文半角标点和成对引号。
- Markdown 标题、强调、链接、列表、引用和代码块。
- Emoji、代理对、组合字符、不同换行和空白。
- 英文缩写、单词边界以及分段拼接边界。
- 同一输入在 Windows、macOS 和 Linux 得到相同结果。

### 24.2 Tool 集成测试

- 流式 Tool 参数完整拼接后只写入一次。
- 相同幂等键重试不会重复追加。
- 文档版本冲突和路径越权不会修改 Draft。
- Tool Result 不包含正文，只包含紧凑状态和统计。
- 写入失败不产生新版本，统计失败不返回虚假成功。

### 24.3 Agent 行为测试

- 普通回答不触发统计或 Draft 写入。
- 文稿模式不在聊天 Content 中重复正文。
- 模型收到不足、合适或超出预期的实际字数后，能选择继续、停止或询问，而不会把 Tool 状态当作用户话语。
- 模型完成写作后通过停止 Tool Call 正常结束，不依赖 `finish_draft`。
- 最大 Tool Loop 轮数和取消机制能够终止连续写作。

## 25. Draft 开放决策

以下细节尚未由产品规则确定，实施前需要用样例确认：

- 连续数字是否按一个字计数，以及小数、百分比和日期的边界。
- 日文假名、韩文、拉丁字母以外文字的计数规则。
- 标题等可见结构文字是否全部计入文稿字数；当前建议计入，仅排除格式标记。
- 是否在 Tool Result 和 GUI 中展示整篇文档、当前章节或当前场景的总统计。
- `cleodoc-richtext-v1` 的最终格式、解析器和可见文本定义。
- Draft 版本的数据库结构、保留策略以及它与 ChangeSet/Git Revision 的映射。
- `write_draft` 如何复用通用文档投影、局部编辑和并发保护，而不暴露内部 ID 或 Revision。

这些开放项不能阻塞已确认的主流程：文稿直接通过 `write_draft` 写入、正文不在聊天中重复、Tool 返回本次写入的精确统计、模型通过是否继续调用 Tool 表达继续或完成。
