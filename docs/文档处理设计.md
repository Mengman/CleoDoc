# CleoDoc 文档处理设计

> v0.1 基线：字符范围读取与 Markdown 全文写入；CDM 节点编辑和 Draft 协议是 v0.2 目标
>
> 适用范围：文档 Application Service、Agent Tool 和 v0.2 作品工作室
> 相关文档：[产品需求](./PRD.md) · [技术架构](./TECHNICAL_ARCHITECTURE.md) · [CDM 设计](./CDM_DOCUMENT_FORMAT_DESIGN.md) · [开发计划](./DEVELOPMENT_PLAN.md) · [Tool Call 设计](./TOOL_CALL_DESIGN.md)

## 1. 文档目的

文档处理是 CleoDoc 的核心基础设施，不只是“读取和覆盖一个 Markdown 文件”。随着产品发展，LLM 读取的文档内容还需要携带稳定节点、资料引用、用户批注、重点标记、格式、知识状态和其他结构信息，并支持安全、精确、可审批的局部修改。

本文统一记录：

- CleoDoc 如何使用 CDM 向 LLM 表达文档内容。
- LLM 如何通过 Node ID 读取、插入、移动、修改和删除文档节点。
- Node、Mark、节点身份和文档 Revision 的编辑语义。
- Tool Result、审批、压缩投影和安全边界。
- 后续批注、引用、格式和结构化编辑的研究方向。

当前已经实现的 `read_project_document` 使用字符偏移读取，`write_project_document` 只支持创建或全文替换。本文所述 CDM 节点读取和局部写入仍是待开发设计，不得在实现状态文档中标记为已完成。

## 2. 已确认的产品需求

### 2.1 不使用视觉行号

CDM 不使用行号作为文档读取或编辑坐标。文档的视觉换行由页面宽度、字体、字号、缩放和渲染器决定；同一段文字在不同展示环境中的行号并不稳定。

LLM 直接读取带 Node ID 的 CDM，并通过 Node ID 定位操作目标。GUI 可以显示视觉行，但视觉行不进入 CDM、不发送给 LLM，也不参与文档写入协议。

### 2.2 Node 与 Mark

CDM 标签分为：

- Node：具有结构或独立语义，可以被单独操作。
- Mark：只表达文字样式，随所在 Node 的内容一起修改。

`<p>` 是最常用的正文 Node，但不是唯一基本单位。`<h1>`、`<li>`、`<blockquote>`、`<table>`、`<tr>`、`<td>` 等同样是 Node。除 CDM Schema 明确声明为 Mark 的 `<strong>`、`<mark>`、`<i>` 等样式类标签外，其他标签都必须包含 `id`。

### 2.3 节点操作

首版支持在目标 Node 前后插入新 Node、删除 Node、替换 Node 的完整内部 CDM，以及在同一父 Node 下前后移动 Node。创建文档和全文替换继续作为完整文档写入操作存在。删除使用明确操作，不把空内容隐式解释为删除。

### 2.4 文档 Revision

Node ID 解决“修改哪个节点”，文档 Revision 解决“模型读取后文档是否又发生变化”。每次节点写入必须带回最近一次读取获得的 Revision；Revision 不匹配时拒绝修改并要求重新读取。

## 3. 设计原则

- **CDM 单一协议**：存储、LLM、解析、展示、编辑和检索围绕同一 CDM，不建立平行 JSON AST。
- **语义节点定位**：操作目标使用 Node ID，不使用视觉行号、数据库 Row ID 或文件字节偏移。
- **Node 与 Mark 分离**：Node 可独立操作；Mark 随所属内容修改。
- **明确操作语义**：插入、删除、内容替换和移动互不混淆。
- **防止陈旧写入**：局部写入必须基于最近读取的文档 Revision。
- **审批优先**：所有 LLM 发起的写入继续要求用户批准，批准前展示目标和变化。
- **原子写入**：校验失败、审批拒绝或写入异常不能留下部分修改。
- **低 Token 投影**：Tool Result 和压缩投影只返回后续决策必需的结构信息，不重复正文。
- **最小首版**：先替换完整 Node 内容和支持同父节点移动，不提前实现字符 Patch 与任意跨层级移动。

## 4. LLM 可见文档投影

### 4.1 直接发送 CDM

LLM 可见的文档内容直接使用 CDM XML，不再建立 `DocumentLine[]` 等平行的 JSON 文档模型。标题、段落、强调、列表、表格和后续批注、引用等信息都使用 CDM 标签与属性表达。

Tool Result 可以在 CDM 内容之外返回文档引用、Revision、选中节点和相邻节点等紧凑控制信息，但正文自身保持为 CDM。读取局部文档时只发送被选中的 Node、必要祖先结构和相邻上下文，不要求发送完整文档。

### 4.2 节点 ID

例如：

```xml
<article id="7k3m9qx2vc">
  <h1 id="b4r8t2w6yz">第一章</h1>
  <p id="c5s9v3x7z0">雨从凌晨开始下。</p>
  <p id="d6t0w4y8a1">林默站在旧车站外。</p>
</article>
```

LLM 可以读取 `c5s9v3x7z0` 及其相邻 Node，然后通过同一个 ID 修改或移动它。节点移动后 ID 不变。Node ID 的字符集、长度、生成和碰撞检查以 [CDM 设计](./CDM_DOCUMENT_FORMAT_DESIGN.md#53-id-格式与唯一性范围)为准。

### 4.3 扩展信息

资料引用、用户批注、重点标记、格式和知识状态将通过 CDM 标准标签、属性或 CleoDoc 扩展表达，不再为这些信息建立另一套按行 JSON AST。`<comment>`、`<reference>` 及范围锚点的最终结构见 [CDM 设计](./CDM_DOCUMENT_FORMAT_DESIGN.md)中的待讨论事项。

## 5. `read_project_document` 未来 v3

### 5.1 定位

当前 `read_project_document` v2 已完成 LLM 可见 JSON 扁平化，但仍按字符 Offset 读取 Markdown。未来应升级为读取完整 CDM 或以 Node ID 为锚点读取局部 CDM，不再增加按行读取 Tool。这仍是一次不兼容的 Input/Output 变化，实施时 Tool 版本需要从 v2 提升到 v3。

### 5.2 Input

```ts
interface ReadProjectDocumentInputV3 {
  document: string;
  nodeId?: string;
  before?: number;
  after?: number;
}
```

- `document`：当前项目内的公开文档引用，不能是数据库内部 ID 或任意绝对路径。
- `nodeId`：可选锚点；提供时读取该 Node 及其必要结构，不提供时从文档根开始读取上下文预算允许的 CDM。
- `before`、`after`：可选的同级相邻 Node 数量，用于获得编辑上下文。

### 5.3 Output

```ts
interface ReadProjectDocumentOutputV3 {
  document: string;
  revision: string;
  selectedNodeId: string | null;
  content: string;
  previousNodeId: string | null;
  nextNodeId: string | null;
  truncated: boolean;
}
```

`content` 是完整 CDM 或可独立解析的 CDM 片段。`revision` 是后续写入使用的公开并发令牌。读取结果不返回 `contentHash`、数据库 Row ID、FTS Rank 或其他实现字段。

## 6. 文档写入 Tool

### 6.1 `write_project_document`

继续负责：

- 创建新的 CDM 文档。
- 全文替换已有文档。

已有文档只有在模型明确声明全文替换意图、携带当前 Revision 并获得用户批准后才能覆盖。

### 6.2 `edit_cdm_document`

所有局部 DOM 变更由一个节点编辑 Tool 承担，通过 `operation` 区分语义。一次调用只执行一个操作。

```ts
interface EditCdmDocumentInput {
  document: string;
  baseRevision: string;
  edit:
    | { operation: "insert_before"; targetId: string; node: string }
    | { operation: "insert_after"; targetId: string; node: string }
    | { operation: "replace_content"; targetId: string; content: string }
    | { operation: "delete"; targetId: string }
    | { operation: "move_before"; nodeId: string; targetId: string }
    | { operation: "move_after"; nodeId: string; targetId: string };
}
```

规则：

- `node` 是一个待插入的 CDM Node；其中必需但缺失的 ID 由 CleoDoc 补齐。
- `content` 是目标 Node 的完整内部 CDM，可以包含文本和 Mark，但不能改变目标 ID。
- `delete` 是唯一删除语义，不把空内容解释为删除。
- `move_*` 首版只支持同一父 Node 下的移动。
- 所有内容先经过严格 XML 解析、CDM Schema 和父子嵌套校验。

## 7. 节点 ID 生命周期

- 除 Schema 声明的 Mark 外，每个标签必须拥有 ID。
- ID 在一份文档内唯一，不是数据库内部 ID。
- ID 由 CleoDoc 生成；LLM 新增 Node 时可以省略，不能指定或修改已有 ID。
- 内容修改、属性修改和位置移动保留 ID。
- 删除 Node 同时删除其后代。CleoDoc 不主动复用已删除 ID，但不维护历史墓碑或全局 ID 台账。
- 节点被移动时，与节点绑定的引用、批注和 Chunk 来源关系仍跟随节点；具体字符范围锚点需要单独处理。

## 8. 防止陈旧写入

每次读取返回一个文档 Revision，每次局部写入必须将其作为 `baseRevision` 带回：

- Revision 一致：可以进入校验、审批和写入。
- Revision 不一致：返回稳定错误 `DOCUMENT_CHANGED`，要求重新读取目标 Node。
- 用户、其他 Tool 或未来 GUI 修改文档后，旧 Revision 不能继续写入。

Revision 是公开的不透明文档版本令牌，不等于 SQLite Row ID、文件内容哈希或 Git Commit。其具体生成和持久化方式可以后续确定，但公共语义保持稳定。

## 9. 公共写入结果

局部和全文写入可以共享紧凑的模型可见结果：

```ts
interface ProjectDocumentMutationResult {
  status: "written";
  document: string;
  revision: string;
  operation:
    | "create"
    | "replace_document"
    | "insert_before"
    | "insert_after"
    | "replace_content"
    | "delete"
    | "move_before"
    | "move_after";
  affectedNodeIds: string[];
  createdNodeIds: string[];
}
```

结果不返回正文、`contentHash` 或数据库 Row ID。`createdNodeIds` 让模型知道 CleoDoc 为新 Node 分配的标识。

## 10. 审批与写入流程

所有 LLM 发起的写操作保持 `approval: "ask"`：

```text
读取带 Node ID 和 Revision 的 CDM
→ LLM 选择插入、内容替换、删除或移动
→ CleoDoc 校验项目范围、Revision、Node ID 和 CDM Schema
→ 展示目标节点和修改预览
→ 用户批准
→ 再次校验文档 Revision
→ 原子写入
→ 返回新 Revision 和受影响 Node ID
```

审批界面至少应展示：

- 文档相对路径。
- 操作类型。
- 目标 Node ID。
- 被替换或删除的原文。
- 准备写入的新内容。
- 移动操作的原位置和目标位置。

当前 Tool Interface 只把 Input 交给审批处理器，如何在执行前生成包含旧内容的 Diff 预览仍需单独设计。不能为了快速实现而在审批后才第一次展示被删除或替换的原文。

## 11. 文件安全与一致性

- 所有文档引用必须限制在当前项目授权范围内。
- Tool 参数必须通过 Zod Schema 校验。
- CDM 必须先通过严格 XML 解析、Schema、ID 唯一性和父子嵌套校验。
- 写入使用临时文件、同步和原子替换，不直接修改文件字节。
- 校验失败、用户拒绝、文档变化或磁盘错误不得留下部分写入。
- 写入成功后再返回新的 Revision。
- 局部编辑引擎应实现为不依赖 CLI、Electron 或 Provider 的纯 Core 能力。
- 普通聊天、Tool Result 和 Debug 日志不能意外保存第二份正文事实源。

## 12. Session 压缩投影

文档读取和写入的历史 Tool 参数可能包含大段正文，不能原样进入 Session 压缩。建议投影：

| Tool | 允许进入压缩的信息 |
|---|---|
| `read_project_document` | 文档、Revision、选中 Node、相邻节点、是否截断 |
| `write_project_document` | 创建/全文替换、文档、新 Revision |
| `edit_cdm_document` | 操作类型、文档、新 Revision、受影响和新增 Node ID |

压缩投影不得包含：

- 读取到的正文。
- 写入参数中的正文。
- 用户批注或资料原文。
- `contentHash`、数据库 ID 或内部 Revision。

## 13. 与 RAG 和未来 GUI 的关系

CDM 是 AI、用户、解析器和展示层共用的内部文档协议，见 [CDM 设计](./CDM_DOCUMENT_FORMAT_DESIGN.md)；导入资料的临时 CDM、纯文本切片和原文定位见[资料解析与切片设计](./DOCUMENT_PARSING_AND_CHUNKING_DESIGN.md)，FTS5 和向量存储见[本地 RAG 设计](./LOCAL_RAG_INGESTION_DESIGN.md)。

CDM 和 Node ID 不应只服务于文件 Tool。它们也是统一的 LLM 可见文档协议，用于：

- `read_project_document` 的直接读取。
- RAG 命中的正文证据。
- 场景创作时的上下文装箱。
- 用户批注、资料引用和重点标记。
- Draft 页面与正文编辑器。
- 一致性检查和影响分析结果。

导入资料的 RAG Chunk 拥有稳定公开 `chunkId`、纯文本内容和原文字节范围，不保存临时 CDM、来源 Node ID 或标题路径。当前 RAG Tool 以项目内唯一 title 选择资料并返回 `title + chunkId + content`，不暴露内部 Source UUID、SQLite Row ID、FTS Rank、原文字节范围或索引实现。Tool Result 到正式 CDM `<reference>` 的转换与资料改名语义仍待确定。

## 14. 后续研究方向

### 14.1 多个节点的原子修改

首版一次调用只执行一个节点操作。未来确有需要时，可以在同一个 `baseRevision` 上校验多个操作，通过一次审批和一次原子写入完成。

批量操作必须先解决操作顺序、节点删除后的引用以及移动目标变化问题，首版不提前实现复杂 Schema。

### 14.2 跨父节点移动

首版只支持同一父 Node 下移动。未来跨章节、列表、引用或表格移动时，必须验证目标父 Node 是否允许该子标签，不能为了完成移动生成无效 CDM。

### 14.3 Node 内精细编辑与标注

首版替换 Node 的完整内部 CDM。未来批注、重点标记、资料引用或超长段落编辑可能只覆盖 Node 中的部分文字，需要定义 Unicode 安全的范围坐标、重叠规则以及内容变化后的锚点恢复。

### 14.4 CDM 读取与分页

大型 CDM 不能一次全部发送给模型。需要继续研究：

- Markdown 与 CDM 的转换。
- LLM 可见结构的 Token 成本。
- 格式标记与正文统计的边界。
- CDM 扩展中的格式、批注和知识元数据如何分层表达。
- 基于 Node ID 的前后浏览、子树读取和上下文预算截断。
- 不同 Provider 对大型结构化 Tool Result 的可靠性。

## 15. 当前不做

- 不使用视觉行号作为文档坐标。
- 不在首版实现任意 JSON Patch、unified diff、字符偏移或模糊文本补丁。
- 不让 LLM 直接操作绝对路径、文件字节偏移或数据库记录。
- 不把空替换内容隐式解释为删除。
- 不在首版实现多节点批量事务编辑和任意跨父节点移动。
- 不提前固定批注、重点标记和字符范围的数据库 Schema。
- 不允许 LLM 生成、修改或复用已有 Node ID。

## 16. 待确认问题

1. CDM Revision 的具体生成、序列化和持久化方式。
2. 未提供 `nodeId` 时，读取文档开头的 Node 预算和分页方式。
3. `before`、`after` 的默认值和硬上限。
4. 审批前 Diff 由 Tool、Runtime 还是独立文档编辑服务生成。
5. `edit_cdm_document` 首版是 `full` 暴露还是通过 `project_tool_catalog` 按需披露。
6. `write_draft` 如何复用同一套 Node ID、Revision 和 CDM 写入服务。
7. Draft Tool 的公开文档引用、Revision/更新时间前置条件和幂等键如何统一，不能直接使用数据库内部 ID。

## 18. Draft 写入与文本统计

### 18.1 背景

LLM 很难仅凭自身生成过程准确估计中文文稿的实际字数。在长篇创作测试中，模型给出的估算可能与实际结果相差一千字以上。CleoDoc 需要提供确定性的本地统计，让主笔知道“刚刚实际写了多少”，再由主笔判断是否继续写作、补充内容、修订或向用户询问。

这项能力不是字数约束器：

- 系统不根据目标字数截断、拒绝或自动重写模型输出。
- 普通对话不统计字数，也不向上下文持续注入无意义的计数信息。
- 统计结果只反馈已经成功写入 Draft 的内容，不能以流式片段或模型自报数字代替。

文稿不能先作为 Assistant Content 输出再复制到 Draft，否则会形成重复展示和不清晰的事实来源。机器写入反馈使用 Provider 标准 `tool` 角色，不增加自定义 `agent` 消息角色。

最终采用直接 Tool Call：当主笔决定产出文稿时，不在 Assistant Content 中输出正文，而是直接调用 `write_draft`。正文只进入 Draft，Tool 返回精确统计，模型据此决定下一步。

### 18.2 目标

- 正文只在 Draft 工作区展示一次，不复制到聊天消息中。
- 对每次成功写入提供确定性的字符数、字数和标点符号数。
- 用紧凑 Tool Result 将统计反馈给模型，尽量少占用上下文。
- 允许模型在得到统计后自然地继续写、停止或向用户说明判断。
- 保持 Draft 写入可恢复、可审计、可重试，并保护已批准正文。
- 统计器和 Draft Application Service 可由 CLI 测试，并由未来 GUI 复用。

### 18.3 非目标

- 不要求模型在写作前严格满足指定字数。
- 不为普通聊天内容计算或展示文稿统计。
- 不通过 `finish_draft` 声明“写完”；模型停止调用 `write_draft` 即表示本轮不再写入。
- 不在当前阶段确定最终自定义排版格式、章节总字数展示或数据库表结构。
- 不允许 `write_draft` 直接覆盖用户已经批准的正式正文。

## 19. Draft 核心交互协议

### 19.1 单轮输出模式

每个 Assistant 轮次必须在以下模式中选择一种：

1. **沟通模式**：输出普通 Assistant Content，用于解释、评审、提问和交付说明；不调用 `write_draft`。
2. **文稿模式**：Assistant Content 为空，直接调用 `write_draft`，正文放在 Tool 参数的 `content` 中。

同一轮不得同时输出面向用户的正文和调用 `write_draft`。这能保证正文只出现在 Draft 页面，聊天区域只显示紧凑的写入状态卡片。

### 19.2 Tool Loop 结束条件

`write_draft` 成功后，标准 `tool` 角色把写入结果和统计返回给模型，Tool Loop 再给模型一个决策轮次：

- 需要继续写：再次调用 `write_draft`。
- 需要查询资料或正文：调用相应读取或 RAG Tool。
- 已完成当前工作：不再调用 Tool，输出简洁的交付说明。
- 需要用户判断：不再调用 Tool，说明实际结果和建议并提问。

不设计 `finish_draft`。如果模型认为文稿已经完成，只需停止发起 `write_draft`。Draft 始终是当前可编辑的工作状态，不需要额外的“完成/重新打开”状态机。

Agent 回合遵循统一结束规则：

- 存在 Tool Call：继续 Tool Loop。
- 没有 Tool Call且存在有效 Assistant Content：结束本轮并交还用户。
- Tool Call 和有效 Assistant Content 都不存在：视为无效模型输出。
- 达到最大轮数、总时限、费用上限或收到取消信号：中止本轮，不继续自动写入。

### 19.3 用户可见反馈

聊天窗口不展示 `write_draft.content`，只展示例如“已向第一章追加 1,684 字”的状态卡片。该卡片是本地 UI 投影，不创建自定义 LLM 消息角色。

模型不应把 Tool Result 当成用户发言，不要以“好的，你刚刚告诉我……”等对话格式复述机器状态。需要用户决策时，应直接给出创作判断，例如：

> 当前章节已经写到约 3,200 字，但人物冲突还没有充分展开。我建议继续补充两人的正面交锋，你希望我继续吗？

如果不需要用户决策，模型可以直接继续调用 `write_draft`，无需发送过渡性致谢或确认。

## 20. `write_draft` Tool

### 20.1 与通用文档 Tool 的边界

当前 CLI `write_project_document` 是通用的、逐次用户审批的项目文件写入 Tool；未来 `write_draft` 是主笔创作循环中的专用工作草稿 Tool。二者不能复用相互矛盾的审批、展示和完成语义。

`write_draft` 只修改可恢复的工作 Draft，不直接覆盖已批准正文或作品 Canon。Draft 进入正式正文仍通过后续交付、ChangeSet 和用户审批完成。

### 20.2 输入契约讨论稿

原 Draft 设计提出以下目标契约：

```ts
interface WriteDraftInput {
  documentId: string;
  operation: "append" | "replace" | "patch";
  baseRevision: number;
  format: "markdown-v1" | "cdm-v1";
  content: string;
}
```

- `documentId` 表示当前 Project 内经过授权的文档引用，不接受任意文件路径。
- `operation` 的首个实现可以只支持 `append`，后续再增加 `replace` 和 `patch`。
- `baseRevision` 用于乐观并发检查，防止覆盖用户或其他任务的新修改。
- `format` 明确选择对应的格式解析器和文本提取器，不能靠内容猜测格式版本。
- `content` 是本次待写入的完整文稿；正文不再同时出现在 Assistant Content 中。

该契约中的 `documentId` 和 `baseRevision` 需要与本文的通用文档引用、`updatedAt` 前置条件及“不暴露数据库内部字段”原则重新统一，目前不能直接视为最终公共 Schema。实施前必须完成第 16 节第 7 项待确认问题。

Tool 参数可能由 Provider 以多个流式增量返回。模型适配器必须先完整拼接同一个 Tool Call 的参数 JSON，再进行 Schema 校验和写入；未完成或无法解析的参数不得产生部分文档。

### 20.3 输出契约讨论稿

首个版本至少返回本次写入的三项统计：

```ts
interface WriteDraftResult {
  status: "written";
  documentId: string;
  revision: number;
  written: TextStatistics;
}
```

示例：

```json
{
  "status": "written",
  "documentId": "chapter-01",
  "revision": 4,
  "written": {
    "characters": 2017,
    "words": 1684,
    "punctuation": 225,
    "algorithmVersion": "cleodoc-text-statistics-v1"
  }
}
```

`documentId` 和 `revision` 同样属于待统一字段。无论最终如何命名，Tool Result 都必须紧凑，不重复正文、Prompt 或长篇解释。结果使用标准 `tool` 角色进入当前 Tool Loop；聊天 UI 可以将其渲染为状态卡片，但不得伪装成用户消息。

后续只有在确有产品需要时才增加写入后整篇文档的总统计。首个版本不把章节总字数作为必需条件。

### 20.4 写入语义

- 一次成功调用同时产生新 Draft 版本和该次写入统计；不能出现“文档已写入但结果仍报告失败”的不确定状态。
- 文件或 Draft 事实源使用安全写入；相关运行状态在事实源成功后再更新。
- 同一个 Tool Call 必须具有稳定的幂等键。网络重试、Provider 重放或进程恢复不能造成重复追加。
- 文档版本不匹配、格式不支持、内容为空、Schema 无效或项目作用域不符时，不进行部分写入，返回结构化 Tool 错误。
- Draft 到正式正文仍通过后续交付、ChangeSet 和用户审批完成。

## 21. 文本统计规范

### 21.1 公共类型

```ts
interface TextStatistics {
  characters: number;
  words: number;
  punctuation: number;
  algorithmVersion: "cleodoc-text-statistics-v1";
}
```

`algorithmVersion` 必须随结果保存或返回。未来规则变化时可以重新计算和解释历史差异，不能在同一版本下静默改变算法。

### 21.2 字符数

字符数是 `write_draft.content` 原始字符串中的字符数量：

- 包含正文、格式标记、标点、空白和换行。
- 不对原始内容做 Unicode 规范化后再计数。
- 使用 Unicode Code Point 数量，而不是 JavaScript UTF-16 Code Unit 数量；建议实现为 `Array.from(content).length`。

该定义统计模型实际提交给 Tool 的内容。换行风格如果在保存阶段发生平台转换，不应反向改变“本次写入字符数”。

### 21.3 可见文本提取

字数和标点符号数都先排除格式相关字符，再对可见文本统计。实现必须按 `format` 使用解析器或 AST 提取器，不能用一组正则表达式猜测格式。

以 Markdown 为例：

- 标题符号、强调符号、代码围栏和链接语法不计入字数或标点。
- 标题文字、强调文字和链接显示文字属于可见文本，应保留。
- 链接目标、属性和结构性标记不属于可见文稿，应排除。

CDM 必须提供独立的可见文本提取器，但沿用相同的统计接口。

### 21.4 字数

字数在可见文本上计算：

- 每个汉字字符计为一个字。
- 每个连续的英文单词计为一个字。
- 格式字符、空白和标点符号不计入字数。
- 英文缩写中的内部撇号允许保持为一个英文单词，例如 `don't` 和 `writer's` 各计一个字；撇号本身仍按标点规范计数。

数字、其他语言文字和特殊符号如何纳入“字数”仍是开放规则，首个实现前必须用固定测试样例确认。

### 21.5 标点符号数

标点符号数在可见文本上计算：

- 排除所有格式相关字符。
- 使用 Unicode Punctuation 类别 `\p{P}` 逐字符统计中英文标点。
- 空白、Emoji 和一般数学/货币符号不自动视为标点。

### 21.6 示例

原始 Markdown：

```md
**你好，world!**
```

统计结果：

- 字符数：13，包括四个 `*` 格式字符。
- 字数：3，即“你”“好”和 `world`。
- 标点符号数：2，即“，”和 `!`。

### 21.7 本次写入与整篇文档

`written` 必须对本次 `write_draft.content` 精确计算。未来如增加整篇文档总统计，应在写入成功后的最终文档上重新计算，不能简单把历史分段相加；两次写入的英文、数字或格式边界可能在拼接处形成不同的词法单元。

## 22. Draft 上下文、持久化与 Prompt

### 22.1 上下文与消息持久化

`write_draft.content` 在当前 Tool Call 参数中已经出现一次，Tool Result 只返回文档引用、版本或更新时间、统计和必要状态，不能再次携带正文。这样模型可以立即依据统计决策，同时避免在下一轮上下文中重复同一内容。

用于聊天展示和检索时应遵守：

- 不把 Draft 正文复制为普通 Assistant Message Content。
- 不把 Tool 参数中的正文索引为普通对话正文，否则历史搜索会得到重复内容。
- UI 状态卡片只引用 Tool Call、文档和版本状态，不保存第二份正文。
- 活跃上下文增长后，较早的 `write_draft` 只投影为文档引用、版本状态和写入范围，不包含正文或内部 Hash；模型需要原文时通过受控文档读取 Tool 获取。
- 压缩、历史查询和 Debug 日志必须明确区分 Tool 元数据与文稿正文。

具体数据库字段和 Draft 版本表结构在实现前随文档版本模型一并设计，本文不提前固定 Schema。

### 22.2 Prompt 约束

主笔 System Prompt 应包含等价规则：

> 与用户沟通时输出普通 Assistant Content。需要创作文稿时，不要把文稿放在 Assistant Content 中，直接调用 `write_draft`，并把文稿放入 `content` 参数；同一轮不能混合两种模式。收到写入统计后，自行判断继续写入、结束交付或向用户询问，不要感谢、复述 Tool Result，也不要把 Tool Result 当成用户发言。

Prompt 只规定行为边界，不要求模型预先精确预测字数。精确数字始终由本地统计器产生。

## 23. Draft 异常与协议违规

- 模型同时输出长篇正文和 `write_draft`：视为协议违规，不自动写入 Assistant Content；允许一次有针对性的纠正重试，仍失败则向用户报告。
- 预期产出文稿但模型只输出长篇普通 Content：不通过启发式规则静默转存，避免误把解释或引用写入 Draft。
- Tool 参数流中断或 JSON 无效：丢弃未提交内容，保留原 Draft 版本。
- 写入超时但本地结果未知：用幂等键查询既有执行结果，不能盲目重试追加。
- 文档版本冲突：返回可理解的冲突状态，由模型重新读取或交给用户处理。
- 统计失败：本次写入事务不应返回成功；在无法提供可信统计前，不让模型基于错误数字继续决策。

## 24. Draft 测试与验收

### 24.1 统计单元测试

- 纯中文、纯英文和中英混排。
- 中文全角标点、英文半角标点和成对引号。
- Markdown 标题、强调、链接、列表、引用和代码块。
- Emoji、代理对、组合字符、不同换行和空白。
- 英文缩写、单词边界以及分段拼接边界。
- 同一输入在 Windows、macOS 和 Linux 得到相同结果。

### 24.2 Tool 集成测试

- 流式 Tool 参数完整拼接后只写入一次。
- 相同幂等键重试不会重复追加。
- 文档版本冲突和路径越权不会修改 Draft。
- Tool Result 不包含正文，只包含紧凑状态和统计。
- 写入失败不产生新版本，统计失败不返回虚假成功。

### 24.3 Agent 行为测试

- 普通回答不触发统计或 Draft 写入。
- 文稿模式不在聊天 Content 中重复正文。
- 模型收到不足、合适或超出预期的实际字数后，能选择继续、停止或询问，而不会把 Tool 状态当作用户话语。
- 模型完成写作后通过停止 Tool Call 正常结束，不依赖 `finish_draft`。
- 最大 Tool Loop 轮数和取消机制能够终止连续写作。

## 25. Draft 开放决策

以下细节尚未由产品规则确定，实施前需要用样例确认：

- 连续数字是否按一个字计数，以及小数、百分比和日期的边界。
- 日文假名、韩文、拉丁字母以外文字的计数规则。
- 标题等可见结构文字是否全部计入文稿字数；当前建议计入，仅排除格式标记。
- 是否在 Tool Result 和 GUI 中展示整篇文档、当前章节或当前场景的总统计。
- CDM 的可见文本提取和统计边界。
- Draft 版本的数据库结构、保留策略以及它与 ChangeSet/Git Revision 的映射。
- `write_draft` 如何复用通用文档投影、局部编辑和并发保护，而不暴露内部 ID 或 Revision。

这些开放项不能阻塞已确认的主流程：文稿直接通过 `write_draft` 写入、正文不在聊天中重复、Tool 返回本次写入的精确统计、模型通过是否继续调用 Tool 表达继续或完成。
